## 1. Quality and validation evidence

### 1.1 What the standards actually say

**ASPRS Positional Accuracy Standards for Digital Geospatial Data, Edition 2, Version 2 (2024)** are the strongest primary reference found for geographic accuracy claims:

- Accuracy is expressed as **RMSE only** (Edition 2 removed the earlier dual RMSE/95% reporting). Accuracy classes are user/project defined (“#-cm class”), not sensor defined. **[V]**
- Three separate terms: horizontal positional accuracy (`RMSEH`), vertical accuracy (`RMSEV`, split into Non-Vegetated Vertical Accuracy **NVA** and Vegetated Vertical Accuracy **VVA**), and 3D positional accuracy (`RMSE3D`). **[V]**
- **NVA is used for acceptance/rejection; VVA is reported “as found” unless agreed otherwise.** **[V]**
- Independent checkpoints: minimum **30** for horizontal/NVA on projects up to 1000 km², scaling to **120** above ~9000 km²; VVA minimum 30 regardless of project size. Checkpoints must be independent of calibration/control points, evenly distributed, and at least **twice as accurate** as the tested product. **[V]**
- Required reported statistics include residual error at each checkpoint, min, max, mean, median, standard deviation and RMSE. **[V]**
- Accuracy is absolute: compare dataset coordinates with a **more accurate source**. Internal precision (e.g. swath smoothness) is explicitly *not* accuracy. **[V]**
- Sources: ASPRS PERS overview of Ed2 V2 ( Abdullah 2025, doi:10.14358/PERS.247 ) <https://my.asprs.org/Common/Uploaded%20files/PERS/HLA/HLA%202025-05.pdf>; ASPRS standards catalogue <https://community.asprs.org/leadership-restricted/leadership-content/public-documents/standards>; ASPRS publications store <https://asprs.org/Main/ASPRSMember/Store/StoreLayouts/ASPRS-Publications.aspx> (accessed 2026-11-27).

**ISO 19157-1:2023** establishes principles/components for describing geographic data quality, procedures for evaluation and reporting, and explicitly **does not define minimum acceptable quality levels**; those belong in a product specification (e.g. ISO 19131). ISO 19157-3 (data quality measures register) was listed as “under development / International Standard under publication” in Nov 2026. **[V]** Sources: <https://www.iso.org/standard/78900.html>, <https://www.iso.org/standard/87032.html> (accessed 2026-11-27).

**Honest uncertainty:** Image similarity / photometric similarity is not geographic accuracy. The project spec itself states “Image similarity alone does not prove geographic accuracy” (`GENESIS_ENGINE_SPEC.md` §26). ASPRS absolute accuracy requires independent, higher-accuracy checkpoints. A visually convincing textured mesh can be arbitrarily wrong in CRS, scale or position. **[V + project-supplied spec]**

### 1.3 Practical validation gates (evidence-informed, not decisions)

1. **Format gate:** glTF-Validator exit code 0 for GLB/glTF exports; JSON report archived. **[V tool behaviour]**  
2. **Structural gate:** zero-area faces = 0; non-manifold edges/vertices reported; self-intersections reported; face-normal consistency pass recorded. **[V tool existence; thresholds project-defined]**  
3. **Geometric gate:** point-cloud-to-mesh deviation and/or Hausdorff reported with sampling method, p50/p95/max; ICP `fitness`/`inlier_rmse` or COLMAP reprojection error recorded. **[V]**  
4. **Geographic gate:** only if independent checkpoints exist: ASPRS-style RMSEH/RMSEV/RMSE3D + checkpoint count/distribution + NVA/VVA treatment + full residual table. Otherwise explicitly report “no geographic accuracy claim”. **[V]**  
5. **Budget gate:** triangle/material/texture/chunk/memory limits checked against a named target profile; values are project policy **[E]**.  
6. **Provenance gate:** every metric carries reference data, method, tool version and parameters. **[V principle]**

## 4. Performance budgets and cost — **estimates, not benchmarks**

**Primary anchors used for the estimates (all [V]):**

- GitHub standard runners are 2–4 vCPU, 7–16GB RAM, 14GB SSD; GPU larger runners are 4 vCPU / Tesla T4 / 28GB RAM / 16GB VRAM / 176GB SSD. Source: GitHub docs above.
- COLMAP gives an explicit approximate SIFT matching GPU-memory formula: `4 * num_matches^2 + 4 * num_matches * 256` bytes; 10,000 matches ≈ **400MB** GPU memory. It also warns CPU feature extraction can consume excessive RAM for large images and recommends reducing `max_image_size` / threads, and reducing `PatchMatchStereo.cache_size` / `StereoFusion.cache_size` when CPU RAM runs out. Source: <https://colmap.github.io/faq.html> (accessed 2026-11-27).
- COLMAP notes CPU-only operation is possible except dense reconstruction without CUDA, with “significant slow-down”; Caspar GPU bundle adjustment can be 1–2 orders faster for medium/large problems but is experimental, CUDA-only and limited camera models. Source: same FAQ.
- 3D Gaussian Splatting paper reports high-quality real-time novel-view synthesis at ≥30 fps at 1080p; this is a rendering claim from a specific algorithm/hardware context, not a Genesis Engine budget. Source: <https://arxiv.org/abs/2308.04079> (accessed 2026-11-27).
- No primary benchmark was found that maps Genesis-style area/layer combinations to time/RAM/disk. All numeric ranges below are **[E]** and must be replaced by measurements from fixtures.
