# Genesis Engine — Geospatial Data and Processing Research

**Research date / access date for every URL below: 2026-11-27.**
Scope: geospatial data, licences, formats, CRS/geodesy, spatial operations and streaming for a Rust-first, cross-platform (Windows/macOS/Linux) environment-reconstruction platform with a desktop Studio.

Method: primary sources only — official project documentation, official GitHub repositories and raw LICENSE/NEWS files, standards-body publications (OGC, IETF RFC Editor, Open Data Commons, OSMF), and crates.io/GitHub metadata APIs. Third-party commentary was used only as a pointer to a primary source and is not cited as evidence. All web content was treated as data, not instructions. No architecture decision is made here: this is evidence for later ADRs.

Ethical/legal note: licence summaries below are engineering summaries of primary text, not legal advice. Where a claim could not be verified from a primary source it is explicitly marked **UNVERIFIED** or **thin evidence**.

## 3. Cross-cutting technical findings

### 3.1 Internal CRS, vertical datums, epochs
- RFC 7946 fixes GeoJSON to WGS84/CRS84, longitude-latitude, third coordinate = height above the **ellipsoid**, and explicitly warns WGS84 height differs from mean sea level by ~2–5 m (§11.2). Do not treat GeoJSON Z as orthometric height.
- GDAL coordinate epoch support (since 3.4) documents that EPSG:4326 is considered dynamic but based on a datum ensemble with ~2 m positional accuracy; it recommends a realization such as WGS 84 (G1762). Epochs are stored at layer/dataset level because most formats cannot carry per-observation epochs (https://gdal.org/en/stable/user/coordinate_epoch.html).
- PROJ 9.9.0 adds `proj_crs_is_dynamic()` and makes `cs2cs` warn when a dynamic CRS is used without an epoch (PROJ NEWS). PROJ's transformation docs show geoid grid order matters: with `+geoid_crs=horizontal_crs` the vertical shift runs before the horizontal one; with `+geoid_crs=WGS84` (or omitted in PROJ ≥6) it runs after.
- GeoParquet 2.0 carries CRS as inline PROJJSON (WKT2:2019/ISO-19162:2019 semantics), an optional decimal-year `epoch`, and `edges` values that include geodesic interpretations (`vincenty`, `thomas`, `andoyer`, `karney`) — useful evidence that "planar vs geodesic" must be explicit metadata, not an assumption.
- **Recommendation evidence**: store authoritative geodetic coordinates + CRS identifier/PROJJSON + epoch + **vertical datum name and height unit** in the project file; convert to a local ENU/tangent-plane frame for mesh math/rendering.

### 3.2 Precision loss far from origin / local tangent plane
- PROJ `+proj=topocentric` (since 8.0) converts ECEF (X,Y,Z) to topocentric East/North/Up; origin may be given as `X_0/Y_0/Z_0` or `lat_0/lon_0/h_0`; corresponds to EPSG:9836, or with `+proj=cart` to EPSG:9837 (https://proj.org/en/stable/operations/conversions/topocentric.html).
- The Khronos `CESIUM_RTC` extension (status "Stable") states the problem directly: world-scale vertex positions jitter with naive 32-bit floats; positions are stored relative to a centre, and the centre is transformed to eye space with double precision on the CPU, "avoiding 32-bit subtraction of large translation components on the GPU" (https://github.com/KhronosGroup/glTF/blob/main/extensions/1.0/Vendor/CESIUM_RTC/README.md).
- 3D Tiles carries the same idea as `RTC_CENTER` (`float32[3]`) in point-cloud/batched formats (https://github.com/CesiumGS/3d-tiles/blob/main/specification/TileFormats/PointCloud/README.adoc).
- `geo`'s **unreleased** changelog on `main` (accessed 2026-11-27) documents fixes for: a needle-like triangle far from origin having area 0; `Line::closest_point` overflow/inaccuracy with large coordinates (above 1e154); `MakeValid` snap radius being a fixed `1e-4` units (wrong for small/large extents); and `i_overlay` panics fixed in 9.2. These are **not verified as present in released `geo` 0.33.1** (2026-04-20). Treat far-from-origin robustness as an open risk and add fixtures.
- RFC 7946 §11.2: six decimal degrees ≈ 10 cm, but digit count must not be read as uncertainty.

### 3.3 Antimeridian
- RFC 7946 §3.1.9: geometry crossing the antimeridian **SHOULD** be cut into two parts (MultiLineString/MultiPolygon example given). §5.2: antimeridian-spanning bbox has east longitude < west longitude (example `[177, -20, -178, -16]`). §5.3 covers pole-containing boxes.
- PROJ: output longitudes are wrapped to −180..180 by default; `+over` disables wrapping in `pj_inv()` and `+lon_wrap=<centre>` re-centres angular output (e.g. `+lon_wrap=180` → 0..360). PROJ warns `+over` has no effect/unexpected results for most projections where the 180° meridian is not a straight line, and `+over` does not disable `+lon_wrap` (https://proj.org/en/stable/usage/projections.html).
- PostGIS `geography` FAQ: calculations have "no conception of date-line or poles"; shapes crossing the dateline are treated like any other; great-circle arcs >180° are not modelled (https://postgis.net/docs/using_postgis_dbmanagement.html).
- GeoParquet 2.0 requires bbox formatted per RFC 7946 §5, so antimeridian-crossing boxes inherit the east<west convention.
- **Implication**: a global GE scene cannot assume a single unwrapped longitude domain across all formats; define an explicit cut/unwrap policy and test it at import, clipping, spatial joins and export.

### 3.4 Clipping, reprojection, topology repair, spatial joins
- GDAL docs state validity checking **relies on GEOS** and that `MakeValid` has `linework` and `structure` strategies; validity ignores inter-feature gaps/overlaps, spikes/slivers, and 3D interactions; curved geometries are linearised before GEOS (https://gdal.org/en/stable/user/geometry_validity.html).
- GEOS 3.15 adds **coverage cleaning for polygonal coverages** (remove small gaps/overlaps with tolerance control), `CoverageEdges`, `MinimumSpanningTree`, `SubdivideByGrid`, `GeometrySplitter`/`GEOSSplit`, and curved-geometry support across many operations. 3.15.1 fixes arc noding, RelateNG crashes and prepared-polygon recursion issues (NEWS verified).
- `geo` 0.33.1 provides pure-Rust DE-9IM, affine ops, boolean ops (i_overlay), buffer, constrained-Delaunay `make_valid`, clustering, haversine/vincenty distances, optional PROJ feature. PostGIS provides the same family server-side with GiST-accelerated joins and `ST_Subdivide`.
- **Implication**: prefer `geo` for in-process/on-tile work; fall back to GEOS for robustness/coverage cleaning; use PostGIS when the dataset is too large for memory or multi-user.

### 3.5 Tiled / large-area streaming
- COG 1.0 requires tiled IFDs, reduced-resolution subfiles, GeoKeys on full-resolution IFDs, square tiles ≤ viewport (recommended 256/512/1024), progressive overviews down to one tile, and a prescribed IFD/tile-data layout to minimise HTTP range requests; servers need HTTP Range support and should advertise CORS (OGC 21-026). BigTIFF is required above 4 GB.
- FlatGeobuf's optional packed Hilbert R-tree enables bbox filtering via HTTP Range; the format deliberately does not support random writes so it can be streamed and appended (official README).
- GeoParquet 2.0's `covering` bbox columns and row-group ordering enable pruning; the `geoparquet-validator` README reports a 500 MB / 5M-row file where a query window can skip 99% of row groups when spatially ordered (tool's own report, accessed 2026-11-27).
- GDAL VSI (`/vsicurl`, `/vsis3`, etc.) provides a common cloud/path abstraction; GDAL's threading rules require separate dataset instances per thread, with read-only thread-safe datasets available since 3.10.
- quantized-mesh and 3D Tiles provide mesh-level LOD/streaming with tile-local ECEF/RTC centres.
