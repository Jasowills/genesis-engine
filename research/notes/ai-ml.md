# AI / computer-vision runtimes and models — primary-source research

Research date: **2026-11-27**. All URLs below were accessed on **2026-11-27**.

Scope: local inference runtimes and model families relevant to Genesis Engine (image segmentation / detection, monocular and multi-view depth, image-to-3D / multi-view reconstruction, texture synthesis / inpainting, material recognition, mesh generation/refinement). Evidence comes from official docs, project READMEs, LICENSE files, model cards, release metadata and papers. Web/model-card content was treated as data, not instructions.

Conventions used in the tables:
- **Verified** = claim is stated in a primary source fetched for this note.
- **Vendor claim** = stated by the project maintainers but not independently benchmarked here.
- **Unverified** = not confirmed by a primary source in this session; explicitly flagged.
- "Licence" distinguishes **code** vs **weights/checkpoints** where they differ. This is the single most important diligence axis for Genesis.

### Runtime conclusion (evidence only, no final architecture decision)

- Two runtime candidates have the evidence needed for a local baseline: **ONNX Runtime** (breadth, stability, cancellation API) and, conditionally, **Candle** where a matching Rust model implementation exists. Burn and tract are credible but less mature; LiteRT/ncnn/OpenVINO are workload/hardware-specific; llama.cpp is out of scope for CV.
- Do **not** choose a runtime merely because it is Rust. The runtime decision should follow the exported model format and the operator set actually used. The adapter contract below is designed so the runtime can change without changing capabilities.
- An ONNX-first pipeline does not preclude Apple acceleration: ORT's CoreML EP and OpenVINO EP provide device selection from one session API.

## 3. Licence and commercial-use landmines (summary)

1. **Depth Anything V2**: only **Small** is Apache-2.0; Base/Large/Giant are **CC-BY-NC-4.0**. A naive "use the biggest model" choice silently makes a commercial product non-compliant.
2. **Ultralytics YOLO**: AGPL-3.0 or paid Enterprise licence. Using it as a linked library in a proprietary Studio is not free.
3. **Unlicensed-by-default research code**: DUSt3R is CC BY-NC-SA 4.0; Hunyuan3D 2 has a bespoke Community Licence with territory exclusions, 1M MAU threshold, AUP and an explicit ban on improving other models.
4. **Codes vs weights diverge**: SAM/SA-1B (model Apache-2.0, dataset research-only), VGGT (code commercial-friendly, original checkpoint non-commercial, commercial checkpoint gated), MMSFormer (Apache-2.0 code but "contact authors" for commercial), LaMa (Apache-2.0 code, weight licence unstated).
5. **Attribution/NOTICE obligations**: Apache-2.0 and BSD-3 require retaining notices; Hunyuan3D requires a specific NOTICE string and prominent disclosure that Tencent does not endorse the product.
6. **Third-party/toolchain licences**: TensorRT, ORT DirectML/CoreML NuGet/Apple terms, TRELLIS submodules, ONNX Runtime's telemetry, MMSFormer's multimodal datasets — all require separate review.

The adapter contract must therefore carry licence and attribution as **first-class, machine-readable data**, not README folklore.

## 4. Proposed AI adapter contract fields

The following fields are proposed for every Genesis AI adapter (local or external). They are grouped by concern; each is justified by an observed need in the sources above.

**A. Identity and provenance**
- `adapter_id`, `capability` (enum: `segment`, `detect`, `depth`, `multi_view_reconstruct`, `image_to_3d`, `inpainting`, `texture_synthesis`, `material_recognise`, `mesh_refine`).
- `provider` (local-runtime vs external-AI), `provider_version`.
- `model_id` + `model_version` + `revision` (HF commit SHA / release tag) — model cards such as SAM 2.1 vs SAM 2 show that names alone are ambiguous.
- `artifact_uri` and **SHA-256 checksum** (PyPI publishes per-wheel SHA-256; Genesis should do the same for model files) + byte size.
- `license_code`, `license_weights`, `license_url`, `commercial_use` (tri-state: allowed / restricted / unknown), `territory_restrictions`, `attribution_text`, `notice_file`.

**B. Contract / schema**
- `input_schema`: named typed tensors with dtype, shape/rank, layout (NCHW/NHWC), colour space and normalization, plus prompt type (point/box/mask/text/multiview list).
- `output_schema`: named typed tensors with coordinate frame and units (e.g. MoGe depth is metric, OpenCV camera axes; Depth Anything V2 is relative; DA-V2 output is HxW raw depth).
- `semantic_version` of the schema and `postprocess` descriptor (e.g. "mask RLE → polygon", "point map + confidence → PLY/GLB").
- Model-specific capabilities/parameters expressed declaratively (e.g. SAM supports `point`, `box`, `mask`, `auto_mask`; SAM 2 adds video tracking; VGGT accepts 1..N views).

**C. Device requirements and runtime selection**
- `runtime` (`onnxruntime`, `candle`, `burn`, `litert`, `ncnn`, `openvino`, `external`), `runtime_version`.
- `execution_provider_priority` (ORT defines ordered `get_providers`/`set_providers`; CoreML options include `MLComputeUnits`, `ModelCacheDirectory`; DML needs D3D12 interop).
- `device_requirements`: CPU ISA baseline (AVX2/VNNI, ARM dotprod/i8mm/SVE), min RAM, min VRAM (TripoSR ~6 GB; TRELLIS/Hunyuan3D ~16 GB), OS list, optional GPU/ANE/NPU.
- `precision` (fp32/fp16/bf16/int8/int4), `quantization_scheme` (QDQ/QOperator, GGUF type, etc.) and `calibration_dataset_id` where relevant.

**D. Inference settings**
- `thread_counts` / shared-threadpool selection (ORT C API supports per-session thread pools and global pools).
- `batch_size`, `input_resolution`/`resolution_level`, `num_steps`, `guidance_scale`, prompt-specific settings (all observed in MoGe, TRELLIS, FLUX, Hunyuan3D examples).
- `deterministic_seed` where sampling is used (TRELLIS, FLUX).
- `memory_arena_config`, I/O binding flags, graph-optimisation level, cache keys.

**E. Execution control**
- `cancellation`: `CancellationToken` mapped to ORT `RunOptions::SetTerminate()` (documented: callable from another thread, forces `Run` to fail with an error); other runtimes need cooperative checks or process-level termination.
- `timeout_ms` (soft timeout via cancellation + hard timeout at process isolation), `queue_policy`, `retry_policy`.
- `progress`: staged progress events (`model_loading`, `preprocessing`, `encoding`, `decoding`, `postprocessing`, `writing_artifacts`), with denoising/refinement step counts where applicable.
- `error_mapping`: canonical codes — `UnsupportedHardware`, `ModelNotFound/ChecksumMismatch`, `IncompatibleOpset`, `OutOfMemory`, `Cancelled`, `TimedOut`, `InvalidInputSchema`, `LicenseBlocked`, `ProviderUnavailable`, `BackendFallbackUsed` — each carrying raw provider error + backend + model revision for diagnostics.
- `telemetry`: explicit opt-out flag (ORT documents telemetry enable/disable in official Windows builds; OpenVINO documents opt-out) to honour local-first.

**F. Evidence/provenance record per run**
- `input_checksums`, `output_checksums`, runtime/EP actually used, precision, full resolved settings, licence snapshot, and a provenance chain linking outputs back to source imagery. This is needed because a fallback from CoreML→CPU or commercial→non-commercial checkpoint changes both performance and licence posture.

## 5. Realistic first capabilities for an MVP (evidence-based, not a decision)

Strongest candidates by combined licence cleanliness, model size and cross-platform story:
1. **Segmentation / object selection**: SAM ViT-B (Apache-2.0 weights), via ORT ONNX or Candle example; CPU/Apple feasible.
2. **Monocular depth**: Depth Anything V2 **Small** (Apache-2.0), with relative-depth semantics made explicit; avoid Base/Large in a commercial build.
3. **Lightweight detection / building extraction**: YOLOX (Apache-2.0) or other permissive detector; explicitly **not** Ultralytics without an Enterprise licence.
4. **Mask-based cleanup / inpainting**: LaMa big-lama (Apache-2.0 code; verify weights).
5. **Optional geometry boost**: MoGe-2 small/base (MIT code; verify weight licence) or COLMAP (BSD-3) on machines with a GPU.

Deferred / conditional: SAM 2 video (phase 2), VGGT multi-view (gated commercial checkpoint), TripoSR/TRELLIS object generation (narrow use, Linux/CUDA), FLUX schnell (large, gated), Hunyuan3D (licence/territory), MMSFormer (research-grade), DUSt3R (non-commercial).

## 6. Hardware floor (from source statements, not measured here)

- **CPU-only laptop (x86_64 with AVX2 or ARM64 with dotprod/i8mm), ≥8–16 GB RAM**: SAM ViT-B and YOLOX/YOLO26n-class detectors with INT8; Depth Anything V2 Small; LaMa. ORT's quantization doc warns old CPUs without VNNI/dotprod can get *slower* with INT8.
- **Apple Silicon with 16 GB unified memory**: fp16 via CoreML EP (ORT) or Candle Metal; CoreML dynamic shapes and EP op coverage need validation; model cache directory should be content-hash keyed.
- **NVIDIA 6–8 GB VRAM**: TripoSR (~6 GB, vendor), SAM 2 tiny/small; MoGe small.
- **NVIDIA 16 GB+**: TRELLIS (≥16 GB required by README), Hunyuan3D 2 shape+texture (16 GB, vendor), VGGT 1B with several views.
- **NVIDIA 24 GB+**: FLUX.1 schnell 12B in bf16 is not realistic on smaller cards; quantised community ports exist but were not verified here.
- **Windows without NVIDIA**: DirectML EP (or WinML) on DirectX 12 hardware; verify opset 20 limits.

## 7. Thin evidence / gaps requiring follow-up

- MoGe checkpoint licences (HF cards not fetched); Stable Diffusion 2 Inpainting licence (gated, 401); SAM ViT-L/ViT-H exact file sizes; Depth Anything V2 metric checkpoint licence.
- No independent cross-runtime benchmarks were run; all speed numbers are vendor/project claims on specific GPUs (A100, V100, T4).
- ONNX Runtime's GitHub repository was unreachable via both HTML and API in this session; version/licence were verified via PyPI and onnxruntime.ai instead. This should be re-checked from a different network.
- "Windows support" for Torch-based model repos often means "works with enough patience" rather than a tested matrix; Hunyuan3D README claims macOS/Windows/Linux, TRELLIS is Linux-only-tested, MoGe-3 is explicitly macOS-unsupported.
- Material recognition evidence is weak: MMSFormer is a 35-star research repo with a contradictory commercial-use statement. Treat the capability as open.
- External AI providers (cloud APIs) were not researched here; the adapter contract is written to accommodate them but no provider terms were verified.
